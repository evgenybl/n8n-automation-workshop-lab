# The four repairs, for printing

> **For printing.** This is `participant/repairs.md` for paper, written by `tools/print-repairs.js`: each repair's cause and
> fix is left out, because a printout cannot fold it away, and each hint is written out. The causes are in
> `instructor/answer-key.md`. Do not edit this file; edit the participant page and run the script.

Each repair is a flow that someone built and that does not do its job. You get the flow and what a user sees, not the
answer. Start from the symptom: reproduce it, read the answer the flow gave, read the record of what it did, and only then
open the node you suspect. Each repair has three hints, from gentle to direct; open one only when you are stuck, and wait a
minute before the next.

**Which repairs, and when.** Session 1: repair A; repair B if you finish A. Session 2: repair C; repair D if you finish C.

**How to start each repair.** Create a new workflow in n8n, import the broken file named below (as in the lab guide,
*How every stage works*), publish it, and use the form address given. Choose **Reset the office** in the office window
first, so that what you see belongs to this repair. As in the guide, paste every value shown in a grey block; do not type
it; where a box already holds a value, select everything in it first.

**Comparing with the repaired file.** Each repair has a repaired file, which you can import beside your own flow. It listens
at its own path, so that it does not clash with your copy of the broken flow:

| Repair | The repaired file | It listens at | Its form address |
|---|---|---|---|
| A | `workflows/repair-a-fixed.json` | `repair-a` | `http://localhost:3333/form?path=repair-a` |
| B | `workflows/repair-b-fixed.json` | `repair-b-fixed` | `http://localhost:3333/form?path=repair-b-fixed` |
| C | `workflows/repair-c-fixed.json` | `repair-c-fixed` | `http://localhost:3333/form?path=repair-c-fixed` |
| D | `workflows/repair-d-fixed.json` | `repair-d-fixed` | `http://localhost:3333/form?path=repair-d-fixed` |

Repair A is the exception: its repair *is* the path, so its repaired file listens at `repair-a`, the path the form sends
to. Before you try it, delete or unpublish your own repair A flow, if you repaired it, so that only one flow listens there.

> The steps for n8n's own screen were written from n8n's documentation and the workflow files, and were not walked through
> on a screen by a person. Every symptom quoted here is what the broken file did in the lab's automated tests on n8n 2.48.8.
> Repair A was carried out on n8n 2.48.8's screen by an AI agent driving a browser, on 25 November 2026, with n8n started
> without Docker: its symptom, what its hints point to and its fix were as written here. The same agent wrote this
> note, so this was not an independent test. Repairs B to D were not carried out on a screen.

## Repair A: nothing happens

**The file:** `workflows/repair-a-broken.json`. **The form address:** `http://localhost:3333/form?path=repair-a` (this is
the path the website's form sends to; do not change it in the form).

**The symptom.** The flow is published, but sending the sample enquiry does nothing that the office can see: no contact,
no call from n8n. The form shows:

<!-- run: offline repair-a-fixed; reset; form repair-a maya; online repair-a-fixed -->
```text
Status:    404
Answer:    {"code":404,"message":"The requested webhook \"POST repair-a\" is not registered.","hint":"The workflow must be active for a production URL to run successfully. You can activate the workflow using the toggle in the top-right of the editor. Note that unlike test URL calls, production URL calls aren't shown on the canvas (only in the executions list)"}
```

(n8n's hint still speaks of a toggle; in this version of n8n it is the **Publish** button.) If you did publish, the
problem is not the publishing. On a real website, the person who filled in the form would see nothing at all, and nobody
would know an enquiry was lost.

**Hint 1.** The answer came from n8n, not from your flow: your flow never ran. Look at the **Executions** tab: is there a run? Only
the list on the left counts: if you looked at a run of another workflow before, n8n 2.48.8 may still show that run
beside the list, with that workflow's nodes, while the list says *No executions found*. What does it mean when an
address answers 404?

**Hint 2.** The form sends to one address; your flow listens at one address. Find where your flow says where it listens, and compare
the two, character by character.

**Hint 3.** Open **Enquiry arrives** and read its **Path**, one letter at a time. Now read the form's path the same way.

## Repair B: the second enquiry from a known person crashes

**The file:** `workflows/repair-b-broken.json`. **The form address:** `http://localhost:3333/form?path=repair-b`.

**The symptom.** Send the sample enquiry: it is recorded. Now Maya writes again, signing as `M. Rivers` this time: in the
form, change the name to `M. Rivers`, keep the same e-mail, and send. The form shows:

<!-- run: reset; send repair-b maya; send repair-b m-rivers -->
```text
Status:    500
Answer:    {"message":"Error in workflow"}
```

**Hint 1.** Look at the office window's call list. Which call failed, and what did the practice CRM say about it?

**Hint 2.** The CRM refused with 409: it was asked to create a contact that already exists. So the flow thought this was a new
person. Look at the lookup call just before it, in the call list: what did it look the person up by?

**Hint 3.** Open **Look up the contact** and read its query parameter. People write their names in many ways; what is the one thing
that stays the same for this person?

## Repair C: a rejected enquiry is written anyway

**The file:** `workflows/repair-c-broken.json`. **The form address:** `http://localhost:3333/form?path=repair-c`. **The
inbox:** `http://localhost:3333/inbox`.

**The symptom.** Send the sample enquiry; it waits in the inbox. Choose **Reject**. The inbox shows what the flow answered
to your decision:

<!-- run: reset; send repair-c maya; reject -->
```text
Status:    200
Answer:    {"status":"recorded","contact":"C1"}
```

and the office window shows the contact. A person said no, and the flow wrote anyway.

**Hint 1.** Which node decides what happens after the decision? Open the **Executions** tab and the run that carried on after your
Reject: which way did that node send it?

**Hint 2.** In that run, open **Wait for the decision** and look at what it received from the inbox. Which field holds the decision
itself, and which fields hold something else?

**Hint 3.** Open **Approved?**. Which field does it read, and what does it ask of it? Would that be true for a rejected enquiry too?

## Repair D: the flow says done, and no note exists

**The file:** `workflows/repair-d-broken.json`. **The form address:** `http://localhost:3333/form?path=repair-d`.

**The symptom.** Send the sample enquiry twice. The second answer says the enquiry was recorded:

<!-- run: reset; send repair-d maya; send repair-d maya -->
```text
Status:    200
Answer:    {"status":"recorded","contact":""}
```

but in the office window Maya's contact has one note, not two.

**Hint 1.** The answer said "recorded", yet the contact number in it is empty. Look at the office window's call list: which call did
the CRM refuse, and with what status?

**Hint 2.** The CRM refused the note with 401: the call carried no badge header. Find the node that made that call, and also look at
its **Settings** tab: what does it do **On Error**?

**Hint 3.** Open **Add a note**. *Send Headers* is off. And *On Error* is `Continue`, which passes the failure on to the next node as
if it were a result, so the flow answers "recorded".
